# Sensors audit and proposed roadmap

Date: 2026-11-19. Branch: `fix/ui-alignment`.
Status: the original audit was approved; implementation is in progress. See the progress notes below for completed work and remaining limits.

## Scope and evidence

Reviewed the twelve supplied screenshots, native egui sensor pages and charts in both `src/app.rs` files, Linux/local/SSH collectors, Windows collector, and Wi-Fi, Bluetooth and power modules. The Windows power, Wi-Fi and Bluetooth modules are byte-for-byte identical to their Linux counterparts. This is a source and screenshot audit, not a hardware compatibility certification or runtime benchmark.

The requested Gemini planner is unavailable in this session. The audit follows Ponytail: keep native egui, existing collectors, theme tokens and dependencies; prioritize correct information and checked operations before restyling. No services, power limits, cache settings, radios or battery settings were changed.

## Visual direction

Keep the current desktop shell, theme selection, compact sidebar and existing 4-card desktop rows. Improve information hierarchy and consistency rather than redesigning navigation again.

- Header: selected host, relevant device selector, sample interval, state and last-update age. Keep it separate from body scrolling.
- Metrics: compact label/value/unit rows, real observed min/max/average only; details in tooltips or expandable sections.
- Charts: one consistent chart style, timestamped x axis, appropriate units and real gaps; distinguish unavailable from measured zero.
- Layout: fill rows evenly; narrow screens can use 2 or 1 columns while desktop keeps 4 where readable. Five thermal sensors should not leave one tall orphan panel.
- Unsupported hardware: one concise explanation and optional setup detail; no pages of empty charts or realistic-looking mock values.
- Controls: compact, checked actions with pending/result feedback. Separate read-only telemetry from system configuration.
- Themes/accessibility: existing accent/danger tokens, readable secondary labels, keyboard focus, full-value tooltips and sufficient contrast in light and dark themes.

## Proposed implementation sequence

Each milestone is split into focused commits by issue, checked in both crates. Show the UI changes for review after each milestone before continuing visual changes.

## Documentation checked

- Installed `sysinfo 0.31.4` source, `src/common/system.rs:911`: `read_bytes`/`written_bytes` are per-refresh deltas; `total_*` fields are cumulative. Online overview: https://docs.rs/sysinfo/latest/sysinfo/struct.DiskUsage.html
- Linux power supply documentation: attributes may be missing; charge, energy, status and health have distinct meanings and units: https://docs.kernel.org/power/power_supply_class.html
- Microsoft Native Wi-Fi API: documented platform functions for wireless interfaces and profiles: https://learn.microsoft.com/en-us/windows/win32/nativewifi/about-the-native-wifi-api
- Microsoft GPU telemetry explanation: Windows GPU metrics depend on driver support, including WDDM requirements: https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/
- Linux process scheduling interfaces: `sched_setaffinity()` and `setpriority()` take numeric IDs; pidfds provide stable signal targets, but neither scheduling interface accepts a pidfd: https://man7.org/linux/man-pages/man2/sched_setaffinity.2.html, https://man7.org/linux/man-pages/man2/setpriority.2.html, https://man7.org/linux/man-pages/man2/pidfd_open.2.html

## Current implementation status

The changes have been made in focused commits on `fix/ui-alignment` in both application trees. The sections above are historical notes; this section records the current state as of the latest polling changes.

- **CPU and process data:** Local whole-system CPU is normalized from `sysinfo`'s sum across logical CPUs into a 0–100% machine percentage; invalid topology/readings remain unavailable. Remote CPU usage is sampled from counter deltas, missing global and per-core readings remain unavailable, sparse CPU numbering and per-CPU frequency slots are preserved, and process state follows the remote kernel. Local process CPU percentages remain unavailable until `sysinfo` has a prior sample for that process, instead of presenting its first zero as a measured idle value. Local Linux frequency collection also retains processor indices. Local and remote Linux signals use process handles and start identities; Windows force and graceful stop verify creation identity. Priority and affinity recheck identity but remain subject to a small PID race because the Linux scheduling operations are PID-based.
- **Windows Top Apps grouping:** Windows lacks a reliable foreground-app classifier in the current process snapshot, so its rows are shown together under “Processes.” Linux retains the existing name-based foreground/background heuristic.
- **Sensor card packing:** The shared sensor-card layout now balances rows at width breakpoints, preventing five-card pages from leaving a lone card on a second row; the same layout is applied in Linux and Windows.
- **Selected GPU history:** Temperature traces are scoped to host and selected GPU identity so switching adapters cannot join readings from different GPUs into one line.
- **CPU context card:** Removed the remaining governor display and hard-coded unavailable cache/thread/handle fields; the card now shows process count, reported OS/version, and uptime on both platforms.
- **CPU power telemetry:** The CPU page calls kernel-reported package caps power caps rather than PL1 limits. The estimated power profile no longer carries unused governor/preset capability fields.
- **Remote memory telemetry:** Remote memory totals and available values must be present and consistent; malformed memory or swap fields fail the sensor query instead of rendering false zero usage.
- **Remote GPU telemetry:** Utilization, temperature, clock widths, memory totals and power are range-checked before display; invalid readings remain unavailable and unnamed adapters are not given a fabricated model name.
- **Local NVIDIA telemetry:** `nvidia-smi` temperature, utilization and power values now reject non-finite/out-of-range results; VRAM is kept only when used and total counters form a valid pair. Empty adapter rows are skipped.
- **Remote battery telemetry:** Battery numeric values are finite/range checked, cycle counts are not truncated, and unnamed batteries use an explicit unknown label.
- **Remote network telemetry:** The interface list must be present, malformed rows are omitted, and missing rates/counters or wireless classification can no longer be reported as zero or wired.
- **Remote temperature and charge-limit fields:** Sensor limits use the same finite range checks as temperatures, and charge thresholds are accepted only from 1–100 without integer truncation.
- **Remote process telemetry:** Requested process samples must be present; malformed PIDs, names, counters or rates are dropped instead of becoming zero-valued process rows or truncated IDs.
- **Remote CPU and disk rates:** CPU package values and aggregate, mounted and physical disk rates are range checked; invalid rates stay marked unavailable.
- **Remote physical disk inventory:** Incomplete disk rows and malformed partition entries are omitted instead of being rendered as zero-sized HDDs; absent model strings use an explicit unknown label.
- **Socket counts:** Local and remote sensor snapshots distinguish a real zero from unreadable or malformed socket statistics; the UI clears stale history and shows unavailable rather than false zeros.
- **Remote socket details:** Missing `ss` output is marked unavailable; malformed endpoint rows are skipped, while an empty but valid result remains a reported zero.
- **Network counters:** Remote `/proc/net/dev` reads are marked unavailable if a sample is missing or any interface row is malformed; interface aliases containing colons remain intact, overview/Wi-Fi/data-usage summaries show unavailable instead of zero, and stale aggregate graphs are cleared.
- **Remote CPU topology:** Logical CPU count falls back to `os.cpu_count()` on Linux architectures that do not report `processor` rows in `/proc/cpuinfo`; missing/invalid counts no longer become one core.
- **Windows GPU inventory:** Win32 video-controller rows without a usable device name are discarded rather than shown as blank adapters.
- **Process collection:** A process exiting during executable-name lookup no longer causes an unwrap panic in either collector.
- **Storage and network:** Process counter baselines include process identity. Remote process disk/network rates and device/interface rates use their own sampling intervals. Remote disk counters use resolved device names and Linux block topology, with duplicate mounted devices excluded from fallback totals. Disk rates retain an unavailable state for missing baselines, reset counters and unsupported platforms; incomplete totals are not displayed as zero. The Windows collector queries aggregate physical-disk and drive-letter logical-disk performance counters, leaving ambiguous or unsupported mounts unavailable. Local and remote physical inventories exclude stacked block devices; mounted volumes are not fabricated as physical disks. Per-process network data is limited to visible TCP sockets; collection is not atomic with process exit. Remote network interfaces can be selected per host; link state, MTU, MAC and available IP addresses are associated with that interface. IP addresses are queried only on the remote Wi-Fi page and remain unavailable if the host lacks a working `ip` command.
- **Power and batteries:** Remote AC and battery data no longer substitute invented names or power-source states. Multiple recognized AC adapters are combined, multi-battery charge is capacity weighted when possible, and the Power page can select a battery. Charge-derived energy is labeled estimated. The user requested the animated power model; it is labeled as an estimate and is not measured history. Governor controls remain removed at the user’s request.
- **Windows hardware-query failures:** A failed live PowerShell/CIM query now clears cached battery, temperature, GPU and disk-rate measurements while retaining discovered device inventory. The UI can no longer present the last successful sample as current after a failed refresh.
- **Windows physical disk inventory:** The 30-second CIM inventory refresh now queries `Win32_DiskDrive`, validates stable identity and positive capacity, retains prior inventory on query failure, and renders Windows device names without Linux `/dev/` paths. Windows does not reliably report media type through this class, so disks are not guessed to be SSDs and per-device throughput remains unavailable when counters cannot be matched safely.
- **Unknown storage media:** SSD/HDD classification is now optional across local and remote snapshots. UI summaries and cards say “unknown”/“Disk” when the host cannot report media type, and power estimates no longer count unknown devices as HDDs or silently add an SSD baseline. Linux NVMe remains identifiable; missing or invalid rotational metadata stays unknown.
- **Windows AC status:** The local Windows power page now reads AC-line state through `GetSystemPowerStatus`; its documented online, offline, and unknown values remain distinct, including on systems without a reported battery.
- **Empty metric history:** Sensor sparklines now say whether they have no samples or are collecting the second sample, instead of leaving a blank plot that resembles missing rendering.
- **Wireless capability state:** Local and remote interface records preserve unknown wireless classification. Windows no longer labels missing or ambiguous adapter metadata as wired; Wi-Fi and data-usage views show unknown where appropriate.
- **Polling and controls:** Bluetooth and Wi-Fi actions report checked results. Local RAM avoids per-process TCP scans. Remote ordinary telemetry skips process sampling; CPU obtains a lightweight visible-process count; RAM collects processes without per-process TCP; Top Apps collects both. A pending lighter refresh is followed by the needed detailed refresh after a tab switch.
- **Remote verification:** Read-only collectors and targeted fixtures have been checked against the user-provided VPS. Temporary processes created by the checks were used for signal, process-state and CPU sampling tests. A follow-up read-only SSH check confirmed the current VPS exposes all required memory/swap fields, including zero-valued swap totals. The VPS is not a substitute for a remote laptop or desktop with real battery, GPU and wireless hardware.
- **Local PC capability spot-check:** Read-only sysfs inspection on this Intel Linux workstation found four CPU cores, thermal/hwmon and battery interfaces, wireless and wired interfaces, and an Intel DRM device with live frequency files but no `gpu_busy_percent`. Thus a missing GPU load is expected from the unprivileged DRM path on this device; engine load depends on the authorized `intel_gpu_top` probe. This checks host capabilities, not the rendered application UI.
- **Windows native title bar:** The Windows desktop app now uses OS window decorations and removes its custom 24-pixel title bar and hit targets. Linux keeps its existing title bar. Windows compile checks pass; visual confirmation on the target Windows machine remains pending.
- **Windows GPU sensor matching:** Adapter names from Windows inventory and LibreHardwareMonitor are normalized for `(R)`/`(TM)` formatting before matching. GPU temperature accepts the provider labels `GPU Core` and `GPU Temperature`, still tied to the matched hardware parent. Duplicate names remain unavailable rather than attaching a sensor to the wrong adapter.
- **Windows RAM temperature:** Temperature sensors whose label is generic but hardware identity reports RAM/DIMM are categorized as memory and the live value reaches the RAM sensor card. Missing RAM temperature remains unavailable.
- **Windows battery capacity:** The native `Win32_Battery` query now includes reported design and full-charge capacities. These values populate the battery layout in Wh, and charge-derived remaining energy stays explicitly marked estimated; zero/unsupported capacity values remain unavailable.
- **Windows CPU package metrics:** CPU power/temperature matching accepts provider labels that include the package metric suffix, while still requiring a unique CPU, sensor parent, and reading.
- **Windows CPU page layout:** Removed its text-only local fallback; Windows now uses the shared sensor cards, metric history and per-logical-processor layout, with unsupported hardware readings still shown as unavailable.
- **Windows GPU engine fallback:** Samples the optional OS GPU Engine counters, sums valid process readings per engine (capped at 100%), then reports the busiest engine per type only when exactly one adapter is present. It does not fabricate overall GPU load; unsupported counters or multi-GPU hosts remain unavailable. Hardware/driver runtime validation is still needed.
- **Remote GPU temperature association:** The remote collector now carries a generic GPU temperature into the adapter record only when there is exactly one detected GPU and one GPU temperature sensor, preserving device-reported values and leaving ambiguous multi-GPU or multi-sensor cases unmatched.
- **Temperature page fallback:** RAM and storage fallback readings now follow the collector's sensor category instead of searching label substrings, preventing a label such as `GPU Memory` from appearing as a RAM temperature in either app.
- **Memory and storage temperature summaries:** Local collectors, remote Linux parsing, Windows hardware parsing, and both UI fallback paths summarize the hottest categorized memory/storage sensor instead of depending on enumeration order. Per-sensor readings remain available in the detailed list.
- **CPU temperature summary:** Linux local/remote collection and both app fallback paths summarize the hottest categorized CPU sensor, independent of provider order. A uniquely matched native Windows package temperature remains preferred; individual readings stay available.
- **Generic GPU temperature fallback:** When exactly one adapter is present but its provider-specific temperature is missing, both app pages now use the hottest categorized GPU sensor instead of choosing an arbitrary first sensor. Multiple-adapter hosts still require an adapter-specific reading.
- **Local thermal limit validation:** The Temperature page rejects non-finite, non-positive, and implausibly high sensor limits (above 150°C) before displaying them, matching the bounds already applied to sensor readings.
- **RAM maintenance cleanup:** Removed the uncalled Linux cache-dropping shell command and its obsolete check from both collectors; the RAM pages no longer expose the maintenance buttons, so this privileged command had no remaining caller.
- **Cooling and Bluetooth cleanup:** Removed the unused sysfs fan detector, which had no UI or collector callers, and corrected the Bluetooth toolbar comment so it no longer advertises the removed RSSI filter. Current Bluetooth codec claims are absent; cooling remains explicitly unavailable because fan telemetry is not collected.
- **Remote Bluetooth status:** Linux SSH hosts now show read-only BlueZ radio and paired-device status in both apps; unsupported remote operating systems and missing BlueZ are reported explicitly. Scanning and device controls remain local.
- **Responsive Data Usage table:** Narrow sensor panels switch the fixed-width interface table to compact per-interface cards, keeping byte totals and live rates visible without a horizontal scroll area in both apps.
- **Metric-card readability and themes:** Shared sensor stat cards now use the active theme's foreground/muted colors and raise secondary labels to a readable 9.5–10.5 px scale in both apps.
- **Unavailable metric plots:** Sensor card sparklines now distinguish no history, one sample, and repeated unavailable samples; an unsupported GPU engine no longer leaves a blank graph that can be mistaken for a zero reading.
- **Storage histories:** Mounted usage and read/write charts now append the actual snapshot timestamp once per sample. Missing mounted capacity and unsupported rates remain unavailable; physical drive count is no longer repeated as a fake time series.
- **Narrow sensor headings:** Wi-Fi title/status and Power host-title rows now wrap within the available width in both apps, covering long interface and remote-host labels.
- **Top Apps search completeness:** The local Linux and Windows collectors retain every process they collect; filtering and grouping operate on the full snapshot. Both UIs include a regression fixture finding process 300 and asserting that all 300 entries remain searchable. The old 250-row truncation is resolved; the remaining limitation is that the Linux Apps/background grouping is a name heuristic, and process network totals cover visible TCP sockets only.
- **Linux process group labels:** The UI now calls the name-based group “Likely applications” and the remainder “Other processes,” instead of claiming these are definitive foreground/background classifications. Windows continues to show its unclassified local process list as “Processes.”
- **Top Apps unavailable sort keys:** GPU and per-process power columns remain visible as unavailable, and their headers no longer accept sorting clicks against hard-coded zero values; hover text explains the collector limitation on both platforms.
- **Multi-GPU process-table summary:** The Top Apps GPU summary now displays a measured percentage only for a single adapter; multi-adapter hosts show unavailable rather than presenting the first adapter as a system-wide total. Values are finite and range checked.
- **Initial local network rates:** Linux and Windows collectors now seed RX/TX baselines from their initial interface snapshot, so the first refresh measures real counter deltas instead of defaulting every interface to 0 B/s.
- **RAM history series and no-swap hosts:** The RAM history's second series is now identified as swap allocation (it was mislabeled as cached memory). Swap percentage and history are unavailable when the host reports zero swap capacity, while a real 0% remains valid when swap exists.
- **RAM composition accuracy:** The physical-memory bar now compares reported in-use memory with the remainder of total memory. Dirty, free/available, and reclaimable counters remain separate because collectors can report overlapping values; the UI explains this on both platforms.
- **RAM total label:** Renamed the RAM overview's total from “resident pool” to “physical memory,” matching the collected `MemTotal`/system physical-memory value.
- **Windows partition counts:** Preserve a missing WMI partition count as unavailable rather than showing a false zero; a reported zero remains distinguishable.
- **GPU memory history:** Use timestamped reported used-VRAM samples for the selected adapter instead of an always-empty chart; invalid or incomplete counters remain unavailable.
- **Unused GPU history state:** Removed three GPU history queues that had no readers; the rendered GPU histories are already stored by host and adapter identity.
- **Missing local memory totals:** When the OS reports no physical-memory total, Overview and RAM now show unavailable, clear stale RAM history, and avoid drawing a zero-usage allocation bar in both apps.
- **Power model GPU fallback:** The estimated integrated-GPU component no longer uses CPU utilization as a stand-in for GPU activity when GPU inventory is missing; it stays at the model's estimated baseline.
- **Unknown battery lifespan:** Removed the fixed zero-progress lifecycle bar; cycle count, lifespan and condition now remain separate reported fields.
- **Unavailable battery charge:** Charge and energy rails now show a fill only when the underlying reading and denominator are valid; missing state no longer looks like an empty battery.
